# competency-navi（コンピテンシー目標ナビ）

社員が期初に書く**コンピテンシー（行動目標）**の下書きを診断し、
上司が期末に達成・未達を判定できる水準まで引き上げるための支援ツール。

グリーンライフ産業株式会社の社内利用を想定した学習課題として開発している。
第三者によるレビューを受けるため、リポジトリは公開（Public）で運用する。

`index.html` をブラウザで開けば動く。ビルドもサーバーも不要。
末尾に `#demo` を付けて開くと、サンプルを入れた状態で立ち上がる。

## 何をするアプリか

```
  社員が書いた下書き
        ↓
  6つの観点で採点（各5点満点）
        ↓
  観点ごとに「点数」と「何が足りないか」を返す
        ↓
  書き方の型と、その型に沿って書いた例（点数つき）を見せる
```

診断の観点は SMART の法則に沿っている。

| 記号 | 観点 | 見ているもの |
|---|---|---|
| S | 具体性 | 誰の・何を・どの場面で、が読んで分かるか |
| M | 定量性 | 数えられる形で書かれ、上司が確認できる事実になっているか |
| A | 手段 | 結果ではなく、自分が動かせる行動で書かれているか |
| R | 項目との関連 | 選んだコンピテンシー項目に効く行動か（**採点しない。後述**） |
| T | 期限・頻度 | いつまでに・どのくらいの頻度で、が決まっているか |
| ＋ | 報告・振返り | 誰に報告し、ずれたときにどう立て直すか |

## 設計の考え方：審判とコーチを分ける

このアプリの中心にある判断は、**どこまでを機械的なルールでやり、どこからをAIに任せるか**である。

```
  ルールで判定（AIなし・無料・手元で完結）    AIに任せる（未接続）
 ──────────────────────────────      ────────────────────
  ・6観点の点数                       ・改善案の文章を書く
  ・何が欠けているかの指摘                ・R（項目に効くか）の判定
                                    ・達成基準（期末に何を見せるか）
```

**点数はAIに付けさせない。** 同じ文章を翌日診断して違う点数が出れば、道具として信用されない。
ルールで判定すれば、同じ文章には必ず同じ点数が出る。

一方、**ルールには原理的にできないこと**がある。たとえば「変化に応じる」という項目に対して
「部署のやり方が**変わる場面**で新しい手順を試す」と書いた文章を、言葉の一致では拾えない。
だから R は**採点せず「要確認」として本人に問い返す**形にしてある。ここはAIを接続したときに
本来の判定へ置き換わる。指示文の下書きは [`docs/gemini-prompt.md`](docs/gemini-prompt.md)。

## 採点の仕組み

観点ごとに4つの条件を見て、**満たした数＋1点**（1〜5点）。総合点は採点した5観点の平均。

```
  例）M（定量性）の4条件
   ① 単位付きの数字が1つ以上ある        「20件」「5名」「80%」
   ② 2つ以上ある
   ③ 数字で達成ラインが引かれている      「月4件以上」「30分以内」
   ④ 上司が確認できる事実になっている     「シートに記録」「日報で提出」「レビューを受ける」
```

④は、コンピテンシー評価の分野で「可視化（測定可能性）」と呼ばれるもの。
**数を並べただけでは上がらず、記録や提出が入ると上がる。**

減点もある。他人が動く前提の書き方（「〜してもらう」）や、行動の無い成果だけの記述は
A（手段）から引く。「悪くないこと」に点を与えない作りにしている。

### 最低ラインを満たした目標は3.5点を下回らない

次の3つは、人事評価の分野で「これだけは満たせ」とされている条件である。

```
  ① 気持ちを表すだけの曖昧な言葉が無い
  ② 頻度か期限のどちらかが決まっている
  ③ 上司が確認できる形になっている（提出物・記録・レビュー・報告先）
```

これを満たした目標は、数値まで揃っていなくても総合点が3.5点を下回らないようにしている。
社外に公開されている「良い目標」の例を採点したところ2.0〜3.2点となり、
**最低ラインを満たした人に「書き直し」と言ってしまう**状態だったため。
判定の言葉も3.5点以上は「提出できる水準」としている。

## 検証して見つけた欠陥

作ったあとで実際の目標文にかけ、いくつも誤りが見つかった。記録として残す。

1. **数字を書くと点が下がることがあった**
   定量性の条件を「以上／以内／まで／率」という**語**で判定していたため、
   「金曜**まで**に」という期限表現が定量性を押し上げていた。
   → 数字を伴う達成ラインだけを見るよう修正
2. **「以前」「午後」だけで具体性が上がった**
   「時・後・前」を単独の漢字で拾っていた。→「〜の時」「〜を受け」のような形で判定
3. **同じ語を二度数えていた**
   「所長」が報告の言葉としても報告先としても登録されていた。→ 行為と相手に分離
4. **名詞を行動と数えていた**
   「**実施**後**レビュー**」を手段として数え、弱い初稿の手段が満点になっていた。
   →「レビューする」「点検して」のように動詞の形かどうかを見る
5. **役職者への期待を見ていなかった**
   管理職の目標には部下育成や意思決定の行動が求められる。→ 職位に応じて指摘を追加

修正後、弱い初稿は1.2〜1.6点、書き直した文は4.0〜4.6点に分かれる（`test/` で確認できる）。

## いまの限界

- **意味は読んでいない。** 語の有無を数えているだけなので、「毎週金曜に何もしない」と
  書いても期限の点は入る。ふざけた文を弾く仕組みはない
- R（項目との関連）を採点できていない
- 改善案の文章を生成できない（型と記入例で代用している）

いずれもAI接続で解ける。裏を返せば、**AIなしでできることはここまで**という線引きでもある。

## ファイル構成

```
  index.html            画面
  src/scoring.js        採点エンジン（AIを使わない判定はすべてここ）
  src/advice.js         指摘の文面を組み立てる
  src/app.js            画面の動き
  src/competencies.js   コンピテンシー83項目の名称と定義
  src/styles.css        見た目
  test/                 採点の動作確認（node test/score.test.js）
  tools/generate-data.py  コンピテンシー一覧のxlsxからデータを作る
  docs/gemini-prompt.md   AI接続時に渡す指示文の下書き
  data/                 年度ごとの職種別割当（手元のみ。README参照）
```

## 見た目について

人事評価システム「あしたのクラウドHR」の画面にトンマナを合わせている。
社員が評価シートとこのアプリを行き来するため、見た目を揃えることを優先した判断で、
グリーンライフ産業のコーポレートカラー（緑）を使わない**例外**である。
経緯は `src/styles.css` の冒頭に記載。

## 取り扱い注意

公開リポジトリのため、以下はコミットしない。

- 実在する社員の氏名・評価内容・目標文などの実データ
- 社内の評価制度そのものが特定できる詳細な項目表
- APIキー・Webhook URL・パスワード等の認証情報

動作確認やデモに使うデータは架空のものを用意する。
実データが必要な場合は `_private/` に置く（`.gitignore` 済み）。
